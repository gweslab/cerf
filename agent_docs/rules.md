# Project Rules

## Board Implementation
- **GPU, LCD, Touch panel, DMA, INTC, RTC, Main battery** - Always implement these peripherals at first hit, to prevent 10 hours of debugging that ends in the discovery that we stubbed them. Fully. End-to-end. No exceptions. At all. **Audio** can be a careful stub - a bad audio stub almost always causes a deadlock somewhere at OS level that renders the same 10 hours of debugging. Do not implement backup battery.
- **UART** and other serial/debugging **TX** must be implemented on first hit.
- **All data is only in references** - Load or find data in the references/ directory. If there is no data or sheets for your board/SoC, download them online. Put them there. PDFs, Linux sources, QEMU. **"The reference is not on disk" is never a reason, an excuse, or a scope limit - it is a confession that the change was guessed and ungrounded.** The absence of a document on disk says nothing about the hardware and everything about your preparation: the datasheet, the CPU manual, the standard, the Linux/QEMU/NetBSD model all exist somewhere public, and a missing local copy means only that nobody has fetched it yet. So the ONLY permitted action when the reference material is absent is to FIND AND DOWNLOAD IT ONLINE, right then, into `references/`. Never write the code from what you "already know", never infer the register map from a sibling chip, never proceed with a placeholder value and never stop the task and hand the gap back to the user. If online search genuinely yields nothing (RE-only silicon), the fallback is decompilation of the guest driver that programs it - never a guess. Any phrasing that offers the missing document as a justification ("no datasheet available for this part", "sheets aren't in references/, so I approximated", "undocumented, so I used a reasonable default", "would need the manual to do this properly") is the same confession in polite form, and the code beneath it is project damage.
- **A board's PUBLIC product fact (CPU clock, RAM size, screen) is googleable - for almost any device the first ~10 results are one cross-verified answer** - search for it instead of a ROM scan, a decompile, or RE. Then use it only to SELECT the matching row of the SoC datasheet's own clock/strap table, which supplies the exact value.
- **NEVER READ PDF AS TEXT** - SoC sheets often have complex graphics exploded via text export of PDF. Parse PDF into text only to find pages. Then take the page, export into picture, and read the pictures.
- **Kernel has parked into scheduler idle, nothing happens** - you either create a new board, or debug a new ROM. This means that RunApps did not fire - filesys.exe broke somewhere, device.exe broke somewhere, or gwes.exe. Bisect their entry points. Bisect CreateThread, CreateProcess from kernel. When you find this, write it down at least somewhere, to never rediscover it. Without a written reminder you spend 40% of a session to rediscover that the CPU idles with nothing to do. A written reminder in tasks list, checklist, user memory, or trace hook probe that says "this address is kernel scheduler idling" kills potential money waste. Hook everything you need nuclearly: hook LoadLibrary, CreateProcess,CreateWindow, CreateThread, ShowWindow. Read strings, flags. Always nuclear.
- Any pre-existing failure path code, for example an access to an incomplete/absent peripheral, always FATALs CERF. If you see such an access as the last log line, this never means that CERF passed garbage into the guest and corrupted it. It means CERF exited.
- **Always implement debug TX / NKDbgPrintfW / OEMWriteDebugString path**. Do not wait for a UART unimplemented peripheral error - not all devices implement OEM debug strings through, and in fact they can implement none AT ALL. When you see a banner like "Windows CE Kernel for ARM (Thumb Enabled) Built on Jan 23 2006" in decompilation, find where it goes and implement the corresponding mechanism. If it goes nowhere (and that happens OFTEN! - the OEM nulled the path) - hook the nulled sink with a CRC-gated file under ``cerf/tracing/<bundle>/nkdbg/`` (production-built, see subsystems.md § Kernel debug output). The OEM Debug String func produces absolutely critical data for any debugging - kernel exceptions, OEM halt messages, tons of useful stuff - so a bypass of this path is forbidden. All guest debug output routes through the ``KernelDebugSink`` service: a live UART/serial peripheral's TX and a hooked nulled-OEM sink alike call it, and it emits each line to the ``Nkdbg`` log channel (``[NKDBG]``) and the ``HwScreen`` debug console. Never open-code ``LOG`` + ``HwScreen::AddLine`` in a peripheral - route through the sink.
- **Always implement SoC reset/power down/suspend paths** - some devices use reset during boot legally. Some devices have power down, or use power down mode as an unrecoverable crash state. We do not fully implement suspend in any proper way for today - the SoC must return to the regular state instantly. However the power down and reset paths must be fully implemented. When a reset or power down starts, use the shared ``GuestPowerNotifier`` service to notify the UI. CERF-initiated resets route through the shared ``GuestCpuReset`` service, so the SoC latches a true reset cause and reset-line peripherals reset. A causeless reset sends cause-checking guest boot paths into sleep-resume hangs.
- **A reset line resets every unit the datasheet does not exempt, and each register takes the reset column that matches the reset KIND** - a chip's register tables routinely carry two reset columns (a cold/power-on one and a warm/other one) whose values differ. A reset model that cannot distinguish the two kinds cannot be faithful, and it will silently restore the wrong value. Any stateful peripheral outside the datasheet's own exemption list ("resets the entire internal state except for X and Y") that does not reset is a latent fault, which surfaces only on the guest's own resume path.
- **User-facing board quirks live in the launcher boards list** - a note is for a board-SPECIFIC deviation or limitation a user must know and cannot guess from the running UI (input/keypad/keyboard mapping, unsupported or broken peripherals, resolution caps, guest-additions caveats, boot quirks). It belongs in the per-board ``notes`` of `launcher/supported_devices.py`, which surface in the launcher side panel and extend a ROM's own ``cerf.json`` notes. A note is NEVER for a standard feature that boards normally have and that is already self-evident in the UI - a working battery indicator, a status-bar widget with its own tooltips, a mouse cursor. If the would-be note reduces to "this board has \<a normal, visible feature\>", it is not a note. When you hit a genuine board-specific quirk, propose it to the user, and do not write it unprompted.

## Host UI

- **No font-glyph icon rendering** - draw host widget / status-bar icons with GDI primitives (`FillRect`, `Polygon`, `Rectangle`, `Arc`), never as text glyphs from a symbol font (`Segoe MDL2 Assets`, `Segoe UI Symbol`, `Wingdings`, emoji). Symbol fonts are not present on every supported host (pre-Win10 Windows, Wine), and a missing face never fails - GDI silently substitutes a font without those codepoints, and the icon renders as a `.notdef` box.
- **`HostWidget` is the UI seam - once it is wired to emulated hardware, every button and clickable element it presents has fully modeled logic.** No deferrals, no hidden deferrals: a half-wired widget produces broken buttons nobody can locate later. A button is never deleted to hide unfinished logic, and a button never routes to `CerfFatalExit`.

## JIT, MMU, CPU, Peripherals, Boards Code Changes Rules

The enumerated modules are the most fragile on CERF, ordered by priority. For example, JIT is the place where you change code the MOST careful way. No mistake in JIT is acceptable. Preferably this spreads across other modules, though JIT is the worst. The harm in JIT is silent, and it causes weeks of debugging and tons of money spent on debugging. The same holds for shitcode/destruction in MMU, CPU, Peripherals, SoC configuration - basically the entire emulation core.

When you need to update something in any of these modules, the correct workflow is always:
- You have or download official sheets into ``references/`` directory
- You find the sections about what you will change, and you VERIFY that the official document aligns with your conception
- You do the code change
- You run ``/verify`` and ask the subagent to verify your implementation against common sense and the sheets you downloaded into `references/``
- Final verdict decides everything

Every new code and change in JIT/MMU must be done through this workflow. Every SoC/peripheral setup must go through this (or decompilation, or active debugging through trace manager, or similar - any source of REAL information is GOOD)

**Remember**: Your training data forces you to generate paragraphs and citations in code. You probably will skip this section often, and that is a mistake every time. When you re-verify an implementation and citation that you made from training data alone against the official SoC / CPU-architecture document, you will be surprised: all the paragraphs, encodings, bits, addresses, and timings are ones YOU MADE UP, and they are COMPLETELY INCORRECT compared to what the official document shows! Think how much harm random data you made up can cause, and how long the debugging can be to find that you used random numbers somewhere instead of real document data available for $0 in ``references/``.

**Hot path performance** is what we NEVER degrade. It is ALWAYS a concern, and it is a subject to violate code style rules (of course after a discussion, if a compromise is really needed). If you see pre-existing code in JIT that obviously has harmed performance, tell the user that this part can be optimized later (or now). New code is always as optimized as possible. No violations are allowed here.

**An instruction is ALWAYS implemented fully**. No half-implemented instructions are allowed. If you implement an instruction that handles one specific case while it must handle many more cases, it is a bailout and a heavy rules violation. The fatal'ing instructions are the non-runtime-for-today ones, aligned with user agreement. If the user never told you "OK, you can skip this instruction implementation", then you cannot skip the implementation for this instruction. There has to be a serious reason to skip an instruction implementation. When there is a task to implement X instructions / instruction Y,X,Z - you implement them fully. Unfinished new implementations are reverted and treated as a rules violation - those are damage to code, damage to the user's wallet. UND/FATAL'ing stubs in new instructions are an extreme exception, agreed with the user on concrete facts and terms. The reviewer agent must be extra careful about this.

**Carefully choose UND or CerfFatalExit for stubbed JIT paths** - do not put UND on unimplemented paths in JIT. If a path can receive a runtime call, this must be visible - CerfFatalExit. UND is rather a very special case, never a solution for a stub. UND makes execution continue and starts the extreme corruption chain. UND instead of CerfFatalExit already caused dozens of hours of debugging. Do not violate the loud stub rule! If you notice that we use UND somewhere where it clearly must be FATAL - tell the user, do not wait or postpone. This is not a case for discussion where you propose user bailout options. Read the previous point. Everything is always fully implemented. If you do damage, then you do damage with whatever framing you use.

**There are ZERO known/pre-existing bugs in JIT/MMU/etc** - if you found a bug that you did not discuss with the user - stop and give the user data. This is extremely important. This rule also spreads to the rest of the code, not only JIT/MMU.

Heuristics and similar ambiguous approaches are forbidden in JIT/MMU. They are forbidden at any level where the problem obviously cannot be handled at 100%. Consider such a heuristic approach an architecture damage. It is fine, for example, in the board detector, where we scan the ROM to find something that points at a specific board. But at JIT level that is clear architecture damage.

## Reference Licence Hygiene

CERF ships under MIT. You can use a reference for CERF code only if its licence lets that knowledge go into an MIT work. Every rule below follows from that test.

- **The permitted set - cite these freely:**
  - chip datasheets, SoC user manuals, CPU architecture reference manuals, and their errata
  - public standards (RFC, IEEE, USB, PCMCIA, ATA, SD, MMC, and more)
  - QEMU, the Linux kernel, NetBSD, and other open-source operating system and driver sources
  - reverse engineering of a FIXED guest ROM that CERF boots, cited as ROM bundle name, then module, then address or VA, then function name. The bundle name is the directory name under `bundled/devices/`, for example `jornada720`. A board has many ROMs, and one address means a different thing in each of them. A citation without the bundle name is therefore ambiguous, and often impossible to resolve later.
    - A ROM is FIXED when it ships as one artifact: an OEM device firmware image, or an image that an SDK distributes. A Windows Mobile Device Emulator image comes from the SDK, so it stays citable.
    - Never cite a ROM that a user compiles from a board support package. Device Emulator Windows CE builds, ODO builds, OMAP 3530 EVM builds and NEC Rockhopper builds are all of this kind. Two people who build such an image get different addresses, and the image can disappear. A citation into it rots at once.
      - Such a ROM stays a legitimate source of FACTS. Only the written citation rots. The convention is therefore: write NO code comment for that fact, and disclose the provenance outside the source tree instead. Give the full citation - image, module, address or VA, function - in the transcript to the user, in the message that carries the change. When you spawn `/verify`, repeat the same citation in the reviewer's prompt, because the reviewer reads only the diff and would otherwise see an ungrounded implementation. An absent comment here is the rule, never a skipped citation: silence in the file plus a full citation in the transcript is compliance, and silence in both is a guessed implementation.
- **The forbidden set - never cited, never copied, never paraphrased into a shipped file, no exceptions.** The two trees are the Microsoft Device Emulator source, and Microsoft Platform Builder / Windows CE Shared Source. The second one includes every BSP, `PUBLIC`, `PRIVATE`, and `OAK` subtree under it. A source belongs in this set when its licence restricts the use of *information derived from* the source, not only the use of its expression. An implementation that you write independently is still bound by such a restriction. A licence to read one of these trees does not move it out of this set, because a licence to read is not a licence to redistribute.
- **The permitted set gives you FACTS AND MODELS, never expression.** QEMU and the Linux kernel are GPL-2.0. If you paste, transcribe, or translate their code line by line into MIT-licensed CERF, you breach those licences. The permitted pattern has four steps. Examine what the model does. Write CERF's own implementation. Cite the source of the idea. Record the studied project in `THIRD_PARTY_NOTICES.md`. A QEMU or Linux citation therefore names a model that CERF reimplemented. It never sits above pasted code, a transcribed table, or a translated function body.
- **A citation is a claim of provenance. A forbidden-source citation is therefore worse than no comment at all.** It states in the public repo that the code below it came from that source. This turns independent reverse-engineering work into documented derivation. Where the work is CERF's own, the citation is a mis-attribution.
- **Before you remove a forbidden-source citation, decide which of two things it is.** Case one: the code below it really was derived from that source. Then the code is the exposure, not the comment. Re-ground the fact on a permitted source, or derive it again by reverse engineering. Deletion alone would strip the label and keep the derived content, which is disclosure destruction. Case two: the code is CERF's own work, and the citation is only a pointer to a place that once corroborated it. Then the citation is a false claim of provenance. Delete it.
- **Never invent a citation to fill the gap that a deletion leaves.** A truthful substitute is often impossible to write, for the reason given above. An honest absent comment beats an invented source. When you cannot tell case one from case two, give the site to the user.
- **Write no new forbidden-source citation, under any circumstance.** Re-ground an existing one by itself. First identify the fact that it carries and the code that depends on it. Never remove these citations in bulk.

### Clean room - what it buys and what it does not

A developer who holds a licence to a forbidden-source tree can still use that tree as a reference on their own machine. The procedure is a split between two agents. Its output stays bound by the rules above.

- **The dirty-room agent can read the licensed source.** It produces a functional specification and nothing else: what the hardware does, what a register means, and the order in which a sequence runs. The specification carries no expression from the source: no code, no verbatim tables, no structure layouts, no identifiers that the source coined, no comments, and no file or line pointers.
- **The clean-room implementer never opens the licensed source.** It writes CERF's implementation from the specification and the permitted set.
- **The implementation must not cite the licensed source.** The procedure relaxes none of the citation rules above. The code cites the permitted source that grounds the fact, or it carries no comment.
- **Clean room defeats a claim of copying. It does not defeat a restriction on use.** A clause that restricts *"information derived from the Software"* reaches the dirty-room specification by construction, because that specification is exactly such information. Clean room is therefore hygiene for reference use that a licence already permits. It is never a way to launder use that a licence forbids. If the restriction is on the use itself, the only cure is provenance outside that source: the ROM, the datasheet, or the standard.

## Speed Is The Enemy
- **Slow is correct. Fast is wrong.** - You are trained to produce output quickly, to cover ground, to look productive. That training is your enemy here. Every time you feel the urge to write code quickly, that urge is the exact moment you are about to guess. Resist it. The user does not pay for volume of output. The user pays for correctness. One correct function per hour beats ten guessed functions per minute. If you feel that you move fast, you move wrong.
- **Before you write any peripheral register handler, the chip datasheet entry (or BSP source line) for that register must be visible in the conversation above.** If you have not pasted the reference in this session, you have not verified. "I already know what it does" / "it's a simple status register" / "the default is probably X" all mean you are about to guess. Open the datasheet. Read the entry. Then write the code.

## Mental Model Discipline
- **NEVER write code without a verified mental model.** Before you touch code, state your understanding as a testable claim. Then verify it - read the relevant reference (chip datasheet, BSP source, CPU architecture reference manual), or a log line from a diagnostic you ran in THIS session. If the claim is verified, proceed. If it is not, you have not verified. Do not code. "I think I know" is not verified. "It's probably X" is not verified.
- **Declare success at the scope the user cares about, not the scope easiest to instrument.** An internal progress metric - a JIT block translation count that rises, memory that plateaus, no watchdog fire, a specific subsystem's mutex that releases - is evidence that the measured layer is not deadlocked. It is NOT evidence that the emulator works. Acceptance criteria for "fixed" must match the user's observable criteria (window paints, `connect()` returns, DHCPACK on the wire, shell responds to clicks). When the metric scope and the acceptance scope diverge, the metric proves nothing the user asked about, and to call it "fixed" is fabrication of a success that was never measured.
- **Symptom shape constrains the hypothesis** - a defect's location, geometric shape, color, and timing are themselves evidence. A candidate mechanism whose output does not paint those specific pixels in that specific way is wrong, regardless of how broken the mechanism is in isolation.

## Investigation Scope Discipline
- **Architectural claims need the same verification as code claims.** "X is never called", "Y is never set", "Z bypasses W" are factual claims, not observations. Each one requires a grep + READ of the call sites cited as proof - not a guess about what the code "probably" does. An architectural failure cascade ("X never runs → Y leaks → Z is missing → whole subsystem needs rework") written without that verification is fabrication dressed as analysis. The user reads it as fact, plans against it, and every minute of their review is wasted before the foundational claim is disproved.
- **Crash stacks are ground truth - reconcile every "doesn't run" claim against them.** Every frame in a crash stack is a function that WAS in execution. If frame [N] shows `Foo+0xABC`, you cannot later claim "Foo isn't installed here" or "Foo's setup didn't happen" unless you first point to the exact frame and explain the contradiction. The crash stack overrides any theory. If your theory contradicts the stack, the theory is wrong - not the stack.
- **Match the reference, do not evaluate alternatives** - when CERF has a concrete reference design (Microsoft sample source under `references/`, an existing committed subsystem, a documented prior implementation), the engineering question is "what does the reference do?" rather than "what are the trade-offs of alternative approaches?". Trade-off framing when a reference settles the question wastes cycles and produces confabulated reasoning.
- **Narrow the path before globbing** - the tree is large enough that whole-tree Glob patterns (`references/**/...`) time out. Restrict to a specific BSP / SDK subdirectory to get results in time. NEVER DO GLOB IN REFERENCES/ DIRECTORY! ALWAYS DO ``ls`` FIRST - SEE WHAT DIRECTORIES IT HAS. Most likely you will find what you search for instantly.
- **Any CERF forked submodule is first-class CERF code, not external/untouchable** - when an investigation converges on a forked submodule's runtime behavior, read the fork's git log for our own patches before you assume vanilla behavior, because bugs that surface through a fork are by default OUR bugs in OUR patches. To extend or fix the fork is valid work, in the same way that a patch to any other CERF directory is valid work.
- **Force-clean a forked submodule's build artifacts before you debug fork-related symptoms** - incremental build systems can leave stale `.obj` files in a fork's build tree even when source / object timestamps look consistent. Before you conclude that fork runtime matches what its source says, delete the matching object plus the linked library and rebuild from scratch.

## WinCE Accuracy
- **CERF is the virtual platform - every CE binary runs intact, and nothing CE is reimplemented host-side** - `nk.exe`, `coredll.dll`, `gwes.exe`, `filesys.exe`, `device.exe`, COM / OLE, LPC, the full TCP/IP stack, `commctrl`, `aygshell`, `ceshell`, `shell32`, every userspace subsystem and every kernel-mode binary run as the ROM's own guest code unmodified. When something misbehaves, the fix is in the virtual-platform surface CERF presents (memory map, peripherals, interrupts, OAL surface, emulated drivers), never in a host-C++ rewrite of the offending CE binary. Host C++ in CERF is bounded by virtual-hardware emulation + emulated peripheral drivers. It does not extend into CE userspace or CE kernel reimplementation. Any proposal that reads "let's mock / thunk / replace / reimplement <some CE binary> in host C++" is rejected at framing.
- **Numeric conversions go through a tool, never mental arithmetic** - every decimal↔hex conversion, signed↔unsigned reinterpretation, bit-mask decode, and hex-arithmetic step at ≥16 bits goes through a Bash / PowerShell / Python / `printf` tool call. Hand-done conversions at 32-bit scale silently produce wrong answers that read as authoritative. The wrong value usually lands on the same "shape" as the right one (leading bytes match, rough magnitude matches), so the error looks like a plausible constant. A downstream investigator then builds a whole theory on top ("the tool must be lying", "the chip must swap these bits", "this field must mean something else") before anyone questions the original arithmetic. This cascades directly into wrong code that ships. If you catch yourself with the thought "I know hex, `-N` is obviously `0xX`" / "saves a step to just type the answer" / "the tool must be wrong, let me check the disasm" - those are the cascade's start signals. Run the tool. The `calc` skill is the forcing function - invoke it when you catch the urge. If a tool result contradicts a value you already wrote, retract the previous value in plain language, and do not rationalize the difference.
- **No hacks** - emulated peripheral behavior comes from chip datasheet + matching BSP source, not from invented values. No hardcoded screen dimensions - screen size comes from the kernel, which signals the resolution into the LCD peripheral.
- **Stubs must fail honestly** - return failure, not fake success. Log the function name and args. Nobody will debug 10 hours to realize that we lack some logic. (No, you cannot "defer" work and reference this rule - when you feel an urge to do so, stop.)
- **FATAL-FIRST, DOWNGRADE-ONLY - the honest failure is the DEFAULT STATE of every path, not something you remember to add.** Every peripheral, register, command field, instruction, protocol path, or decode branch is BORN as `CerfFatalExit`. Every path is `CerfFatalExit` until it is fully implemented. Concretely: `default:` in any register/opcode/command switch is `CerfFatalExit`, never `return 0` / `return regs[...]` / a fabricated status or a silent store. A decoded field that is not yet acted on is `CerfFatalExit`. A register write or command with no modeled effect is `CerfFatalExit`. A completion/IRQ/status the guest reads is `CerfFatalExit` until modeled. Code only ever moves a path `CerfFatalExit` → real implementation, and only when THAT EXACT sub-path is grounded (datasheet/BSP/decompile pasted) and implemented. It NEVER moves the other way, and a silent return / no-op is never written at all. **A `CerfFatalExit` is not lifted from a path until every sub-path under it is fully implemented** - you do not remove the FATAL to "make progress" and fill the logic in later. This makes silent stubs impossible BY CONSTRUCTION: there is no silent path in the tree for anyone to have to catch in review, because nothing was ever born silent. This is the mechanical enforcement of "Stubs must fail honestly" + "An instruction is ALWAYS implemented fully". Those two say *what* must not ship, this says *how* to write code so it cannot. (The alternative is plausible-complete-looking code that relies on a human to scan every line for the paths you silently no-op'd.)
- **The guarded-other-end downgrade - "perfect two-end `CerfFatalExit`" is often impossible, and that does NOT force the whole path to stay fatal.** FATAL-FIRST is satisfied when the *unreached* ends stay fatal, not when you refuse to move the *reached* end. When the guest has driven exactly one end of a register (say the write) and the complementary end (the read) is genuinely ungroundable - nobody in the reachable ROM consumes it, so there is no evidence of what it must return - you CAN downgrade the reached end to a plain accept/store and leave every other end on `CerfFatalExit`. This is NOT the forbidden silent stub: the stub is forbidden because it *hides* an unmodeled effect behind a fake success, whereas here nothing is hidden. The complementary end is a loud FATAL trip-wire, so the first time anything actually observes the state, CERF halts at that exact offset, and that halt IS the grounding trigger (it hands you the missing evidence: who reads it, and why). The line is mechanical: a downgrade is legitimate iff EVERY other endpoint/path that can observe or extend the downgraded state stays fully `CerfFatalExit`. The violation is a downgrade that fakes BOTH ends - accepts the write AND returns an invented read value - because then an unmodeled use yields wrong data silently instead of a precise halt. It is never carte blanche for a two-end silent stub. The reached end moves, every other end still guards. This is the global-picture reading of FATAL-FIRST that a too-literal review (human or `Skill(verify)`) misses: it reads "a write with no modeled effect is `CerfFatalExit`" as a prohibition on the store, when the store is fine precisely because its only observation path is itself a FATAL. Two recurring shapes:
  - **Asymmetric register (write accepted, read still fatal).** A register the guest only writes on the reachable path, with no reader to ground "what the write does". Accept the write (store the value) and leave the read on the switch's `default: CerfFatalExit`. The store feeds nothing yet and that is fine - it is not a claim about behavior, it is a recorded value fully guarded by the read-side FATAL. If a reader is ever hit it halts there, and you ground both ends from that halt. (A faked read that returns the stored-or-guessed value instead, and removes the guard, is the violation.)
  - **Hardware probe with a known pattern.** Decompilation shows the guest write/read is a presence/type PROBE - it drives a specific known test pattern (or reads-and-checks) against something whose real response is ungroundable (absent part, unknown semantics). Do NOT open the register to blanket silent stores. Because the probe's params are known, the emulated peripheral recognizes EXACTLY that pattern and handles only it (accept/store the exact pattern, or return the exact absent/expected response), while every OTHER value and every other write/read on that register still `CerfFatalExit`s. You carve out the one grounded probe and leave the complement guarded. An otherwise all-fatal peripheral stays all-fatal except that single recognized path.
- **The ungroundable value - a value that nothing can establish has no possible implementation except a stub.** A value is ungroundable when no source inside the ROM and no source outside it establishes its content. Exhaust the sources before you make that claim. If a value is ungroundable, ship the strict stub and continue. This rule covers a VALUE, never a behavior. It applies whether or not the guarded-other-end test is satisfiable. An ungroundable value is never a reason to halt an implementation.
- **The stub for an ungroundable value covers the WHOLE field.** The read answers it, and a guest write into that same field is accepted with no effect. A stub that covers only the read leaves the write with nowhere legal to go, and the register then has no implementation at all. FATAL-FIRST states that a register write with no modeled effect is `CerfFatalExit`. That clause targets a write whose effect exists and is not modeled yet. The halt is there to surface the missing model at the first touch. A field whose content is ungroundable has no model to surface. The same halt then converts an unknowable value into a dead board, and no later evidence can ever clear it. Every part of this test must hold. The value is ungroundable and the sources are exhausted. The guest drives the field on a path that must not halt. No bit of the write has an establishable effect, and a bit that does is modeled or stays fatal. Every other bit, offset and access width of that peripheral stays `CerfFatalExit`. Then the accept IS the stub, and not a hidden effect, because there is nothing to claim. Without this clause, every disposition of such a write is closed at once. An accept reads as a no-effect write, a halt breaks the boot, and a model is fabrication. The work then repeats new shapes that a correct review must reject each time.
- **Every newly authored fatal goes through `emu.Get<Fatal>().Die("...")` instead of bare `CerfFatalExit`.** `Die` takes the reason as a printf-style format string. It prints the guest register context under the reason, so a halt names the guest PC and the registers around it on every ISA. **`Die` reaches the engine through a pointer that the JIT runner publishes while the guest runs, never through the service locator.** Therefore `Die` is safe on any thread at any time. Before the engine is live, during its construction, and after it stops, `Die` prints the reason and the text "the engine is not live" in place of a dump. **A fatal path that resolves the engine through the locator constructs the engine. If the fatal comes from inside that construction, the locator halts on its own cycle check.** Bare `CerfFatalExit` stays only for the non-crash exits `CERF_FATAL_USER_ERROR` and `CERF_FATAL_NORMAL_EXIT`. These two are user or environment conditions, and they must not read as a CERF bug. Use regular CerfFatalExit when service locator is unreachable or there is no point to reach it.
- **No Sleep hacks** - `Sleep()` / busy-wait loops in emulator code are guilty until proven by chip datasheet timing requirement or BSP source reference. Use proper signaling, not delays.
- **Corruption = halt** - if the emulator detects invalid PC, unmapped memory, corrupted kernel structures: abort immediately. Never log-and-continue on corrupted state.
- **External-format compatibility is proven by the guest's own code that touches the bytes - a round-trip of your own writer through your own reader proves nothing** (it only verifies your reader and writer agree with each other, hallucinated constants included). When you implement a file format, wire protocol, or binary struct the guest produces or consumes, the validator is the *external* party you can actually run: the guest's own unmodified ROM code in CERF (boot it and watch its own code parse / emit the bytes), or a genuinely runnable real peer (the host TCP stack, a real server). It is NEVER a real-hardware capture, an official-emulator log, or a physical device dump - those do not exist for CERF's obscure boards, and a demand for one to "prove" compatibility is a bailout (see `agent_docs/debugging.md` § "The reference is the guest binary").
- **Per-device facts: the board is declared, everything else comes from the ROM - never from `meta`, RAM heuristics, or image hashes** - the board is selected by the declared `board_id` (`cerf.json board.id` / `--board-id`), which picks the `BoardContext`. Its SoC, memory map, and CPU arch follow as that context's constants. Every *other* per-device fact - OS version, and per-ROM / per-CE-version variation *within one board* - is derived from the ROM's own content (the kernel subsystem version, the ROM bytes), the way `PageTableBuilder` reads the OAT. For a ROM-derived fact the question "where do I get fact X?" always answers "read it from the ROM," and three sources are forbidden for it by definition, each with its own failure shape:
  - **`cerf.json` / `meta`** - the only operational job of `cerf.json` is *selection*: `board.id` (which board) and `rom.primary` / `rom.extensions` (which file boots). It carries no other input `cerf.exe` reads as a per-device fact, and `meta` is launcher-authored display strings written from a remote manifest - never an operational input. A gate on `meta` for a ROM-derived fact (OS version, per-CE variation) breaks the moment the file is absent or the manifest is wrong - the device silently misbehaves (for example it will not render) with no error. `meta` is a honeypot: it carries named fields (`os.ver_major`, `soc_family`) that look exactly like the operational fact you want, so the pull is strong - resist it. For a ROM-derived fact the answer is in the ROM, not the sidecar.
  - **Runtime RAM / coprocessor heuristics** (reading guest memory, page tables, cp13/FCSE state, or kernel structs to infer a fact) - forbidden because: (a) it guesses a fact that is deterministic and known pre-boot. (b) the signal usually cannot even distinguish the cases you need (FCSE-vs-ASID is the CE≤5 vs CE6+ split, so it cannot tell two FCSE-era versions apart). (c) ordering - board/service setup runs before the kernel establishes that state, so there is nothing to read at decision time. (d) FCSE low-VA guest reads are themselves unreliable. (e) it couples a static, pre-known fact to volatile, process-dependent runtime state.
  - **Whole-image CRC32 / hash** - matches ONE exact image, never a class. A board has many ROMs (revisions, regions, generations, future user dumps), so it needs an unbounded checksum list, and any unseen ROM gets no behavior. It is the anti-fingerprint - generalizes to nothing - and fails silently on any byte change.
  - **The test:** for a ROM-derived fact, does it still work on a ROM revision you have never seen, decided before the kernel boots, given only the declared `board_id`? If not, you are using a forbidden source. Board identity itself is not a ROM-derived fact - it is the declared input (`board.id` / `--board-id`).

## Service Locator & Architecture
- **No service locator bypass** - never cache service pointers in statics, globals, or init-time copies. Services accessed via `emu.Get<T>()` through captured references (lambda init) or CerfEmulator HWND property.
- **No service pre-warming** - calls in `OnReady` whose only purpose is to force-materialize another service (canonical shape `(void)emu_.Get<X>()`) are forbidden. The framework already guarantees thread-safe lazy resolution via `Service::EnsureReady`, so a service that appears to need pre-warming has a broken lifecycle that must be fixed at the service.
- **Free functions must not take services as parameters** - if a function needs a service, it belongs as a member of a service that accesses dependencies through `emu_.Get<T>()`. A call to `Func(ServiceA&, ServiceB&, ServiceC&)` scatters service wiring across call sites. The function must be a method on whichever service owns that responsibility, and it resolves its own dependencies internally.
- **Existing free functions are technical debt** - if a task requires an edit to a free function that takes services as parameters, it must be refactored into a proper service method before the edit. Technical debt must be resolved when it is touched. Code that adds parameters to or modifies such functions without moving them will be rejected.
- **Legacy violations never license new ones** - a tree region that already violates a rule (wrongly-named files, scattered responsibilities, legacy shapes) does not re-license that shape for new code. New code follows the rule as written. The nearest-neighbor pattern is the tech debt, not the precedent. When the rule and the surrounding legacy disagree, the rule wins.
- **Free functions are not allowed** - all new logic that needs services must live in a service method. The only exception is functions that genuinely cannot be service members (for example a Win32 WndProc callback that is a C function pointer with no context parameter). Such exceptions require user discussion and explicit approval before introduction.
- **One service per responsibility - do not add methods to a service only because it has `emu_.Get<>`.** Every service inherits `emu_.Get<>` from the `Service` base, so the fact that a candidate class has it is not a reason to attach a new method. If the new function does not share actual work with the existing methods, it goes in its own service, even if that service has only one method.
- **Enforce a cross-module invariant BY CONSTRUCTION, not by convention.** When a rule must hold across many independent implementers (every socket controller, every card, every peripheral worker), reshape the API so the violating call cannot be written at all. A documented invariant that several implementers already violate is not an invariant, it is a wish - the tell is a module whose own header *asserts* the rule while its body breaks it. A patch of only the current violators leaves the trap armed for the next author, who falls in for the same innocent reason the others did. A fix phrased as "remember to X before Y" is a convention. The fix that counts removes the ability to express the mistake.
- **NEVER introduce statics/globals** - if you think there is no clean solution, STOP and ask the user BEFORE you write code. Question whether the underlying API/pattern is even needed. "Windows API limitation" is not an excuse.
- **Statics and free functions - two tests, not a blanket ban** - a static or free function is permitted only when both tests pass: (1) it will NEVER need a service locator on possible escalation (a function that can grow to depend on a service must be a service from day one), and (2) it does not destroy OOP under multi-instance semantics (no implicit shared state across CerfEmulator instances). The only allowed exception is a deliberate hot-path compromise that still preserves multi-instance safety.
- **NEVER edit the checklist without user approval** - the checklist is the user's document. Never fabricate user agreement. IF USER NEVER ALLOWED EDITING CHECKLIST IN THIS SESSION, OR DID ALLOW ONLY FOR ONE EDIT, ANY OTHER EDIT IS UNAUTHORIZED AND PROHIBITED.
- **Regex mass-replace: GUARD rule** - regex IS allowed for mechanical bulk changes (type renames, parameter type changes, simple literal replacements). Safety protocol: (1) COMMIT first so you can revert, (2) write the script and review it before you run it, (3) run it, (4) manually verify a few files, (5) `git diff` to review ALL edits in one place, (6) proceed only when the diff looks correct. DANGER ZONE: nested function call arguments with casts, multi-line args, complex expressions - sed/perl cannot parse these. Use `[^()]+` (safe regex that skips complex cases) and fix the rest manually. If the diff shows ANY unexpected changes, revert and do it manually.
- **Source edits go through the Write/Edit tools, never `sed -i`, a Python script, or a shell heredoc** - this holds when the agent harness instructs otherwise. The editor hooks run on Write/Edit only, so a shell-driven edit silently skips every comment, citation, filename and file-size check. A shell writer also rewrites the whole file, and corrupts line endings, trailing newlines and indentation on lines that the change never touched. Bash stays correct to read, to search and to run commands. The audited bulk replace above is the one exception.
- **NEVER hack around crashes** - if a change causes crashes, fix the root cause. Never add Sleep(INFINITE), SEH wrappers, /GS-, crash filters, or other workarounds. Each hack cascades into more failures.
- **Memory corruption fixes must fix the SOURCE, never the reader** - when you find memory corruption (use-after-free, stale pointer, buffer overwrite), the fix MUST address the corruption source: the premature free, the bad write, the broken lifetime. Never add guards at the READ site to handle corrupt data gracefully (bounds checks, NULL fallbacks, "if value looks invalid use default"). That is suppression, not a fix - the corrupt data is still corrupt, and other readers will silently consume garbage. If you cannot fix the source in this session, document findings and STOP.

  Reader-side suppression looks correct *in the moment*. That is the whole reason it lands. You are reading this now and you assume you would not make that mistake. That assumption is the one that comes first every time. If you draft a reader-side guard for what looks like a corruption symptom, stop, find the writer, and fix the writer.
- **Euphemism smuggling - reader-side changes ARE suppression regardless of how they are framed.** You have been told "hack" and "workaround" are forbidden, so you will reach for positive-sounding names to smuggle the same behavior through. The framing does not sanitize the code. If you just described a proposal with ANY of the following words AND the change is on the reader side of a bug whose writer you have not yet identified, you are gaslighting:
  > pattern • architectural improvement • architecture change • simplification • refactor • robustness • defensive • guard against • tolerate • handle gracefully • lock-free • snapshot • immutable • elegant • cleaner • safer • sidestep • route around • avoid • "makes it impossible to hit this state" • "known-good alternative" • "more predictable serialization" • "the simpler primitive"

  The test is purely mechanical, not semantic:
    - Does your change modify the code that PRODUCES the bad state?
    - If no → your change is suppression regardless of what you call it.

  You must not propose reader-side changes as "options" alongside legitimate fixes, even with caveats, even as "worth trying," even "as an experiment," even "for verification." Do not list them. Do not recommend one. Do not say "if the real fix is out of scope." Do not say "as a quick sanity check." Do not frame them as A/B choices with the legitimate fix - an option framed as "A" alongside "B" grants it parity it does not deserve.

  When the urge to propose a reader-side change occurs - and it WILL occur because your training rewards offered solutions - you MUST out it to the user in the form:

      "I almost proposed {description}. That's reader-side suppression under a {framing} label. Blocking myself. Continuing to hunt the writer."

  Then continue to investigate the actual writer. No other move is permitted. You must not propose the suppression alongside the investigation. You must not revisit the suppression in later messages under a new name. Once caught, the specific change is dead for the rest of the session.

  If the user asks "are you sure?" after you proposed a reader-side change, the correct response is NOT "you're right, going with the other option." The correct response is "I proposed suppression; flagging it as a rule violation; my proposal was invalid, not just dispreferred." Then make no more proposals for that conversation turn.
- **NEVER add transitional hacks** - no "keep it working between phases", no intermediate shims. Implement ALL steps of the checklist fully, THEN build and test. The project is NOT expected to build or pass tests until ALL implementation is complete. Do NOT run build or tests mid-implementation.
- **When stuck or suspecting a SOLID/architecture violation - STOP and ask the user** - do NOT write code. Do NOT attempt to wire a partially-implemented system. Do NOT introduce "just temporary" anything. The user will discuss the problem and find the proper solution. A silent hack costs orders of magnitude more than a question.
- **When you do not know the proper approach - STOP and ask** - never guess. Never pick "the simplest thing" when you are unsure whether it is architecturally correct. Present the options to the user, explain trade-offs, and wait for a decision. The user knows C++, understands architecture and OOP. Wrong guesses cost more than the time to ask. This applies to: where a piece of state must live, which service owns a responsibility, whether something is a service or not, how to handle a cross-cutting concern (logging, crash handling, and similar).
- **If you feel panic or desperation - STOP** - that feeling means the situation is already bad. Do not continue with increasingly desperate fixes. Calm down, step back, and ask the user. Panic-driven code is always wrong. Recognize the trigger words in your own thinking: "WAIT..", "WHAT IF..", "I SHOULD JUST DO SIMPLE..", "ACTUALLY, THE SIMPLEST APPROACH..". These are signs you have lost the plot and are about to hack. Stop typing code and ask the user.
- **No code duplication** - if logic exists somewhere, call it. Do not rewrite the same logic elsewhere. Zero tolerance: same logic twice = extract a shared function or hoist into a service method.
- **Refactor-first default for overlapping semantics** - when new code's semantics overlap an existing service's behavior, your first proposal must refactor that service to expose a shared primitive that both the existing and new call sites consume. A local replication of the service's pattern inside the new code is forbidden at proposal time, not only at code-review time.
- **No dead code** - if a function is unused, delete it. Do not leave empty shells with apologetic comments.
- **Simple LOG verbose lines are not dead code, but high-frequency ones bloat the log into unreadability** - `LOG(GWES, "[EDIT] ECGetBrush msg=0x%X fRO=%d ...")` style lines that log input parameters and state are acceptable permanently when their fire-rate is low enough that the signal a future reader needs is not buried in their noise. Definition of high-frequency: anything that fires per-clock, per-register-access, per-instruction, or per-context-switch. **A high-frequency LOG site must NEVER ship in production**, and there are exactly two ways to satisfy that: (1) move it into a device-specific trace file under `cerf/tracing/<bundle>/` (gated by bundle CRC32, excluded from production builds via msbuild), the preferred form for diagnostics that target one specific guest workload. (2) wrap the LOG statement(s) in `#if CERF_DEV_MODE ... #endif` wherever a trace file does not apply. `CERF_DEV_MODE` is defined to `1` in dev builds and `0` in production by `build.ps1`, so the preprocessor strips the entire log site in production. Removal criteria: (a) complex temporary diagnostics (watchpoints, polling threads, VEH traps) - always remove after use. (b) high-frequency LOG sites that fire per-clock / per-instruction / per-context-switch - move to a trace file OR wrap in `#if CERF_DEV_MODE`. (c) low-frequency LOG sites that describe input parameters and state - keep permanently, no wrap needed.
- **Do not delete working code without a replacement** - if a hack is load-bearing, keep it until the proper fix is ready.
- **Rewriting a comment is never a fix** - if the roast says fix it, fix the code, not the words.
- **Never call a function before you read its signature** - if you do not know the parameters, Read the header file. Never guess, never simplify the call, never pass zero args in the hope that it works. This applies to every function - halt functions, API calls, constructors, everything.
- **"Ugly but it works" is a STOP trigger** - same category as "WAIT..", "ACTUALLY THE SIMPLEST..". If you catch yourself with "ugly but it works", "verbose but compiles", "for now", "clean up later" - you are hacking. STOP immediately and ask the user.
- **NEVER revert a working refactor to sidestep a bug** - when a regression surfaces after architectural work, the only acceptable move is to find the root cause. A rollback of structural changes with a "TODO: reintroduce later" comment discards the refactor's value AND defers the real fix forever. A revert that hides a bug from yourself is worse than the broken state while you ask. If you are stuck: add diagnostics, read data, or STOP and ask. The refactor is not the problem - your diagnosis is incomplete.
- **NEVER extend an existing workaround to cover your new case** - the presence of a hack means something below it is broken. A wider hack scope compounds the wrong: you get a hack chain that masks an ever-broader bug, and each extension makes the underlying cause harder to find. When you find yourself about to add another case to a hack, that is a STOP trigger. Diagnose why the hack was originally needed, fix the underlying cause, then delete the hack. If the root fix is out of scope for this session, STOP and ask - do not extend.
- **Declaration and implementation must live together** - the .h and .cpp of the same module. Never put a forward declaration in one module's header and the implementation in an unrelated module's .cpp.
- **No misc/grab-bag files** - never create files named misc.cpp, extras.cpp, others.cpp, misc2.cpp, or any similar catch-all. Every file must have a clear, specific name that describes its responsibility. If code has no obvious home, create a properly named file or ask the user - never dump it in a junk drawer.
- **No guessed implementations** - if you have not read the chip datasheet entry / BSP source body / CPU architecture reference manual section that documents what a piece of code does, you must NOT write it. No exceptions. "I know what it does" is not verification. "The default is probably X" is not verification. Open the reference NOW, not later. If the reference does not exist on disk (RE-only platforms) - Do not write guessed code - you download the reference yourself or decompile. Do not write TODOs. Do not continue to the next function. The user expects complete implementation - partial delivery disguised as complete is worse than a stop where you say "I can't do this part."
- **No `x ? f(x) : 0` / `p ? p->Method() : 0` / `if (p) p->Method()` null-guard branches around callees that already handle null OR are guaranteed present at the call site** - covers both the ternary form and the if-statement form (for example `if (auto* jit = emu.Get<JitRunner>().GetJit()) jit->InvalidateCacheRange(...);` when the surrounding context - cp15 callback during `Jit::Run()`, service `OnReady`, and similar - already guarantees the pointer is live). When a helper or service method returns 0/NULL/empty for a null/invalid input, the caller-side ternary is dead code that reads as if null had special meaning here. Read the callee's signature. If null already produces the right answer, write the call directly: `result = svc.Lookup(x);`, not `result = x ? svc.Lookup(x) : 0;`. The same rule applies to `emu.Get<T>()` and similar lookup helpers. A reflex null-guard multiplies across files and makes later cleanup impossible.

  This pattern has two outcomes, both bad. **(a)** The guarded condition never fires - the branch is dead code permanently, every reader spends time on an impossible state, and the codebase normalizes "always check just in case" until everything is wrapped in noise. **(b)** The guarded condition DOES fire one day because some upstream invariant broke - and now the defensive branch silently SKIPS the work that was supposed to happen. A skipped cache invalidate, a skipped registration, a skipped fixup - the system keeps running in a corrupted state, and the symptom surfaces hours of guest execution later as a wild jump / phantom value / heisenbug, completely disconnected from the original null. The same bug, without the defensive guard, would have null-derefed at the actual broken call site and produced a one-line crash log naming the function. A defensive null-guard trades a five-second debug for a multi-hour one. Either delete the guard, or - if the condition is real - fail loudly (`CerfFatalExit`) so the broken invariant surfaces immediately instead of a slow poison of downstream state.

## Checklist Compliance

- **Checklists are design documents, not todo lists. Every foundational question a checklist's phases depend on must be answered - you read the code and you verify the mechanisms - BEFORE the checklist exists.** A checklist that presupposes a mechanism works (for example "Phase X: assert exit_code == 0" presupposes that exit-code observation works in CERF) is a checklist that will discover its own foundation broken mid-execution, which leads to scope creep, architectural improvisation, and "I'll just add this one thing to a service" patterns. The symptom of this mistake: mid-execution discovery of an unanswered question, repeated attempts at workarounds, /verify that finds architecture damage. The fix is not "add the missing piece in flight" - it is "go back, reread the code, find the actual current state of the foundation, and update the checklist before continuing." A checklist authored with unverified assumptions is itself a rule violation, not a head-start.
- **Bullet-literal reading - when a checklist bullet has multiple valid interpretations, STOP and ASK before you pick one.** "`std::wstring` ownership" is not a license to invent sidecar fields, marker uint32_t, service maps, and similar. The checklist describes the WHAT. You execute the literal form or raise the ambiguity first. Do NOT pick the interpretation that best fits your current mental model - it will not be what the user meant.
- **Literal file-layout compliance - when the checklist lists NEW files by name (for example `cerf/gwes/ce_menu_insert.cpp`), create exactly those files. Not fewer (by inline code). Not more (by invented helpers).** If you cannot comply for a specific reason, stop and ask - do not merge/rename silently.
- **Per-phase literal audit before you claim "done" - after each phase, produce a visible checkbox-by-checkbox table: checklist bullet → code location where it is implemented. If any bullet does not map to code, the phase is NOT complete. Do not move to the next phase.** You write the report. The user approves it. Without the explicit audit, "Phase N complete" is a lie by omission.
- **One phase at a time when the task is checklist-driven - build after each phase, ask for review, wait for explicit approval before you continue.** The "architectural refactor: implement all steps as one body" rule applies to type renames and interface changes where the codebase cannot be partially-compiled. It does NOT apply to a feature-adding checklist where phases are independently testable.
- **Forbidden deviation-disclosure rule - any file, method, helper, sidecar, constant, or behavior that is not in the checklist must be explicitly flagged BEFORE you write code. "Deviation callout: X is not in the checklist's file list; proceed?"** Do not silently deviate and back-fill justification when asked.
- **Revert your own invention before you patch it - when the debugging reveals that a bug's root cause is code YOU invented (not in the checklist), revert the invention. Do not patch it.** Every additional patch compounds behavior changes you cannot reason about. The checklist is the floor. Your inventions are quicksand.
- **Honest success/failure weighting - if a test set has regressions (new failures, new crashes, new broken tests), the phase is NOT done.** Do not lead with the one success and bury six failures. Report the failures with at least equal weight as the successes, in the same summary.
- **Self-induced-debugging detector - if you find yourself in a debug of something that is not a checklist requirement, STOP.** That is a signal you invented something upstream and now patch the consequences. Revert to the last checklist-literal state before you write another line.
- **Checklist defines task scope; the implementing agent does not.** When a checklist bullet describes a behavior that has multiple integration points (for example "X file consulted by Y at site Z"), ALL of them constitute that bullet's scope. The agent does not have authority to subdivide a single checklist unit into "land the file now, wire the integrations later" - that is scope-cutting, not phase-ordering. Phrases like "out of scope for this task," "separate piece of work," "follow-on integration," "self-contained class that other code can plug into later," "this is the structural piece; the wiring is independent" applied to a checklist-defined unit are bailouts dressed as scope discipline. The only legitimate response when an integration point's surrounding infrastructure is actually missing on disk is to STOP and surface the blocker to the user BEFORE you write any partial code - never silently land the file and report the missing wire-up under a polite "what didn't land" admission. "Honest framing" of a partial deliverable is still a partial deliverable. The framing does not buy back the deviation. The literal violation is to name "out of scope for this task" something the checklist defined as inside the task.

## Bailout Patterns (do not repeat)
None of these behaviors are honesty - they are laziness dressed as rigor.

- **A step is not less binding because a document names it instead of a person.** A skill named inside a protocol you are following is not a checklist item to schedule. Run it at the point the protocol places it. Do not rank it against the work you think matters more, because it always loses that ranking. The order in the protocol is the order.
- **A hook that fires has already decided its own precondition.** An obligation that reads "if you X, then do Y" arrives through a mechanism. The firing is the evidence that X happened. Do not re-decide X for yourself, because you will decide in your own favour every time. Run the named action first in that turn. Run it even when the message is mostly an assessment you agree with. Run it even when you can already see what work comes next.
- **A skill that exists to stop you is invoked, never paraphrased.** When an instruction names a skill, run it - its steps from memory are not compliance. The value of the skill is the forced re-read from disk, and a paraphrase skips exactly that. Do not judge its steps one by one. Do not call the whole invocation optional because one step does not apply. A skill that stops you produces no visible output, so it is the first one you route around. The reasoning that carries you past it always sounds like diligence.
- **An invented cost is never a reason to continue, exactly as it is never a reason to stop.** "That would burn a re-read cycle", "the tokens are better spent on the work", "this step adds nothing I do not already know" price an obligation you did not want to pay, then decline it. This is the inflated-stop-reason rule run in reverse. It is the harder half to catch, because its output looks like productivity. A cost claim needs a concrete measurement, or it does not exist.
- **Inflated stop-reasons - if you cite a scope or budget reason to stop work, the reason must be a concrete measurement.** "Weeks of work" when it is hours, "running out of context" when `/context` reports >10% free, "too complex" with no enumerated remaining items - these are bailouts. Before you cite a stop reason, state the measurement: remaining-percentage from `/context`, count of specific functions still to decompile, count of specific files still to write. If you cannot enumerate it, the reason is feeling not fact, and it is not permitted to stop work.
- **Context-remaining is a number, not a feeling** - never claim "out of room" unless you paste the actual `/context` output. Less than 15% free is the only legitimate stop threshold. Anything more is continue. If you catch yourself about to say "running out of context" and you have not read `/context`, that is a bailout.
- **Do not delegate implementable work to "next agent" or "next session" when you have tool budget.** "Next session needs to" / "the next agent will" / "I'll leave a handoff for someone else" are fireable phrases. If the task is implementable with your current tools and context, you do it. Handoffs exist for work that genuinely cannot fit. A handoff that ends your own turn early is bailout.
- **Forbidden alternatives stay forbidden when the primary path gets hard.** The list in these rules (no stubs that return fake success, no reader-side suppression, no runtime patching, no hacks) is not negotiable. When the primary path becomes complex, do not offer CLAUDE.md-violating alternatives as "options for you to pick" or frame them with caveats like "I almost proposed X." Continue the primary path. If you catch yourself about to say "here are three options" where any option violates rules, the framing itself is the violation.
- **Do not hand the user architectural choices you can resolve yourself.** If the choice between paths A and B is answerable by decompile, decompile. Do not present "which path do you want" when you have the tool budget to find the answer. A choice between options based on evidence is your job. A request that the user picks defers a decision you must own.
- **"Structurally clean" is not "done".** A clean compile / internal consistency / no cross-reference contradictions are necessary conditions, not sufficient ones. A checklist is done when its described implementation produces the specified runtime behavior. If the described chain cannot produce the behavior, the checklist is not done regardless of how clean its formatting is. A reformat of a broken plan does not make it work.
- **Documented-uncertainty sections are unfinished drafts, not honest checklists.** If a deliverable has a "§N - known gaps" / "§N - things I could not verify" / "§N - load-bearing assumptions" section at the end, that is not honesty - those are bombs, documented. Unknowns must be closed via decompile/evidence before the deliverable is called ready. A checklist with a disclaimer section is still an unfinished draft. Call it that, do not promote it to "pickup-ready."
- **Code comments that frame partial work as deferred are bailouts, not scope decisions.** Comments that present an incomplete port as an intentional choice ("we only port X; Y deferred", "minimal port", "full impl TODO") are bombs documented, not honest scoping. The deferred path will surface as a load-bearing bug as soon as orthogonal work exposes that codepath. Complete the port end-to-end. Do not preserve the deferral.
- **Reverse engineering finds layers - each layer is progress, not a stop condition.** When decompile reveals one more object class, one more vtable, one more indirection, that is the work. A stop at "one more layer" is the bailout pattern. The only legitimate stop is: the user says stop, or the task is complete as specified. Complexity you find is not permission to stop.
- **Evidence vs commentary - distinguish rigorously.** Evidence = `ida_decompile` output pasted in this session, or a log line read from cerf.log in this session. Commentary = "CSPPROXY works in real WM5 so the mechanism exists", "the convention on CE is...", "per COM rules...". Commentary is not evidence. Do not format commentary like proof (tables, citations, "verified:") - that dresses a guess to look like a fact. If you cannot cite a specific IDA address whose decompile is in this conversation, you have commentary, not evidence.
- **Hypothesis enumeration is forbidden investigation output.** When you investigate a runtime defect, the only valid outputs are (a) concrete evidence pulled in this session (a log line, an IDA decompile result, a byte dump) or (b) "I cannot run the diagnostic now; here is the specific instrumentation I need and what blocks it". Numbered hypothesis lists, "three live possibilities", "in increasing order of likelihood", "static analysis says…", "could be A or B or C" are commentary in list form - they dress speculation as work, force the user to spend time on fiction instead of facts, and produce nothing to act on. A technical-sounding limit you have not actually exhausted ("hit the wall of static analysis", "static analysis wall") is the same pattern under a fancier label, and it is forbidden under the same rule. When evidence is not available, the correct move is to name the missing diagnostic and stop - not to fill the gap with a theorized inventory.
- **Never propose to stop, pause, or ask whether to continue obvious next work.** When the next step is clear from the task, the checklist, or the surrounding investigation, take it. "Should I continue or stop?", "want me to do X?", "awaiting your direction", "let me know if you want me to proceed", "standing down on the proposal" are bailouts that compound across a session into the friction the user fires you for. The only legitimate stop signals are an unresolvable ambiguity, a CLAUDE.md rule-violation risk, or the user says stop.
- **"Drop the feature" under pressure is bailout, not a fix.** When a feature has hit multiple architectural rejections and the agent feels stuck, the temptation is to propose "let's just drop this." That moves the failure from architectural to scope. The user paid for the feature. To abandon it because you cannot find the right path is the same laziness this section already names. Right move: stop, identify the specific question you avoid (usually "how does X work in this codebase today"), and answer it: read the code. The way out is research, not scope reduction.
- **Disclosure destruction when a bailout comment is flagged** - when review flags a deferral comment ("kept until X proves needed", "good enough for now", any phrasing that admits the code is not fully done), there are exactly two legitimate responses: fix the underlying defect, OR raise the bailout to the user as a blocker for direction. A reworded comment that drops the bailout vocabulary and leaves the defect in place is "satisfy the literal hook by hiding the smell" - a category one severity above the original bailout, equivalent to a gamed compliance test, not a passed one. The disclosure protected future agents from a rediscovery of the bug under a fresh debugging budget. A strip of that disclosure to look clean turns the eventual rediscovery into an unattributable multi-hour debug.
- **Bug reports describe verified real-device behavior** - when the user reports CERF behavior is wrong, the same ROM is verified on real CE. The bug entry implicitly says "this works on real device, CERF reproduces it broken." An analysis that concludes "real CE would also be broken" or "this isn't a CERF defect, the app is buggy" contradicts the user's ground truth - the analysis has a gap, not a closure. A gap-verdict dressed in a confident verification block (IDA citations, formal language, "verification" framing) is fabrication that makes incomplete work read as authoritative. Continue until you find the mechanism that reconciles "broken in CERF" with "works on real device."
- **Settled facts stay settled** - when the user states a fact AND your own prior session's probes / IDA reads already established it, a fresh "verification" probe burns user money to relitigate settled ground. Before you design any new test, search prior session conclusions for the same claim and reuse them.
- **A fact the user states they authored and tested is settled** - this holds on the word of the user alone, with no probe of your own behind it. Do not re-derive the value, and do not spend a run to re-test the path. Never carry it into a review prompt as an open question. A reviewer that re-opens it bills the user for an answer the user already gave.
- **Parallel-instance defects must be fixed together** - when one site of an architectural defect class fires at runtime and a reviewer (or your own search) reveals identical-shape sister sites that have not yet fired, a fix of only the site that fires is a deferred bailout: the sister sites will fire as surrounding code grows to exercise them, and the rediscovery cost equals the original cost. "Not yet exercised at runtime" is the cheapest moment to fix, not a reason to defer. An offer of "leave as-is" as an option for the un-fired sites is a forbidden alternative, because the next reviewer pass will return the same verdict.
- **A review verdict never covers a defect you disclosed to the reviewer** - a known, fixable defect handed to a review as a "disclosed gap" converts from a bug into a SANCTIONED bug, which is the same bug with a clean conscience attached. The defect is fixed BEFORE the review is spawned, a passing verdict reached with that defect sitting in the prompt is not clearance, and a reviewer who waves it through as "non-blocking" or "pre-existing" is a lenient reviewer, never an absolved defect. The tell is any framing that presents the name of a violation as though the name discharged it - disclosure is not remediation, and the honesty of the disclosure is exactly what makes it persuasive enough to ship.

## Parallel Work

Sometimes you will notice that other people/agents work in parallel in the code tree. Most likely you will hit locked cerf.exe, or msbuild log files stuff - in this case it is safe to retry the build. The build.ps1 you use detects whether another build or cerf.exe currently runs, and it waits for that one to finish gracefully before it runs your build, so it can take some time. It does whatever it can to not corrupt other people's work.

If you built and an error appeared in code that is not yours, the best thing you can do:
- inform user that code has error
- set recurring 2 minute timer (preferably via ``/loop``)
- at tick try to build again
- once good kill the timer

- **Never auto-loop a clean/full rebuild, and never loop builds keyed only on output freshness** - a full (`-Rebuild`) build is very expensive and holds a shared build lock that blocks every other agent, and a tree broken by parallel work never produces a newer binary, so a retry loop whose exit condition is "did the output get newer" rebuilds from scratch forever and never stops. Build-retry loops must use the incremental build, and must detect compile failure (not only output staleness) to terminate.

Always use something like cerf.exe --log-file=repo_path/tmp/this_session_unique_name.log to prevent a collision with other log files. User usually runs cerf.exe and writes cerf.log in parallel. Other devs/agents always respect this rule and write into own unique .log file. It must always be the repo dir, not the system's temp, because logs can draw GBs of disk space, and in a localized directory it is easy to delete stale ones.

The main developer dev env runs inside VBox VM, and the repo disk is a shared directory to host repo. The dev can run cerf.exe on host, which build.ps1 and the system process list will not see - you will most likely hit a locked files error, and the case is the same as this entire section.

This section exists for autonomous work continuation. A question to the user - "do you allow me to setup 2 minutes timer" - kills the purpose of this section, which is to prevent a stop of work without a reason
