# Internationalization

This implementation is a proposal for maintainer review. It introduces a shared
runtime catalog for the Win32 UI and the Python launcher. It does not change
emulated hardware, guest language, ROM metadata, or saved-state identities.

## Catalogs

`langs/en.yml` is the required default catalog. All other catalogs are partial
overrides of it. Both frontends read the same UTF-8 YAML files at runtime. New
translations and changes to existing text require no compilation.

```yaml
name: "한국어"
messages:
  common.cancel: "취소"
  task_manager.process_count_partial: "프로세스 {count}/{total}개"
```

Message identifiers are stable semantic keys. Editing English wording does not
change its identifier. Equal words used in different contexts may have separate
keys. Internal names, config values, icon filenames, and resource identifiers
never use translated text.

Filenames use ISO 639-1 or ISO 639-2 language codes, optionally followed by an
ISO 3166-1 alpha-2 or UN M49 region: `en.yml`, `ko.yml`, `fr.yml`, `pt-BR.yml`.
The current implementation accepts this subset of BCP 47, not every possible
language tag. An unavailable regional catalog falls back to English.

The schema requires exactly `name` and `messages`. `name` is the language's
native display name. `messages` is a flat mapping from identifiers to text.
Use quoted strings or YAML block scalars. Both parsers treat plain scalar text
as text; explicit non-string YAML tags, nested values, duplicate keys, NUL, and
multiple documents are rejected. Files are limited to 1 MiB.

Missing message entries use English. Unknown keys and invalid placeholders in
an override are reported and ignored. A missing or malformed selected catalog
uses English entirely. A missing or malformed English catalog is an installation
error, because the application cannot guarantee complete default text.

## Formatting

Templates accept named placeholders such as `{device}`, `{count}`, and `{error}`.
Names match `[a-z][a-z0-9_]*`. They may repeat and appear in any order. `{{` and
`}}` represent literal braces. Argument values are substituted once and are not
parsed as templates, so paths, exception text, and names may contain braces.

Translations must have the same set of placeholder names as English. Positional
fields, Python expressions, printf specifiers, attribute lookups, and arbitrary
format specifications are not supported. Numeric formatting happens at the
caller before substitution. Missing or extra caller arguments are programming
errors and are tested independently of language fallback.

```cpp
emu_.Get<UiLanguage>().Format("task_manager.process_count_partial", {
    {"count", std::to_string(shown)}, {"total", std::to_string(total)},
});
```

```python
t("task_manager.process_count_partial", count=shown, total=total)
```

Plural selection, locale-aware number/date formatting, RTL layout, accelerator
allocation, and native UI language switching while a guest runs are separate
extensions to discuss with maintainers. This version uses count-neutral phrasing
where possible and does not pretend to implement those features.

## Selection and UI lifecycle

The optional root `cerf.json` field `language` stores the launcher's selection.
The default is `en`. This is a proposed config-schema addition, not an existing
upstream contract. Device JSON files and state images do not store UI language.

The Win32 `--language=CODE` argument overrides root configuration. `UiLanguage`
is a per-emulator service: it loads the English catalog and selected override
in `OnReady`, and caches wide strings for Win32 calls. Its selected language
and returned text pointers stay valid for the emulator's lifetime. The portable
UTF-8 `TranslationCatalog` has no Win32 dependency or process-wide state and can
be reused by future frontends.

The launcher discovers valid `langs/*.yml` files for its settings list. On
language change it reloads the selected catalog and rebuilds the main UI in the
same Tk window, preserving the device selection, search query, and pane split.
Open secondary dialogs retain their existing labels; newly opened dialogs use
the selected language. No periodic widget scan, reflection, source-string
matching, filesystem watcher, or extra process is involved.

The launcher passes its effective language to CERF on startup. CERF sends its
effective language in the existing transactional query when asking the launcher
to open properties/settings/about dialogs. This also covers CERF started
directly with a command-line language override. Already running CERF instances
use their startup language until restarted.

## Build and deployment

C++ uses `yaml-cpp` through the existing vcpkg manifest. Python uses PyYAML
6.0.1, which supports the launcher's CPython 3.7 runtime. MSBuild copies the
shared catalogs to `langs/` beside `cerf.exe`; the launcher build copies the
same catalogs to the bundled tree. A full installation has one external
catalog directory shared by CERF and the launcher. The standalone installer
also carries that same source directory as a frozen data resource.

Translation files are intentionally external. The package must include the
catalog directory; distributing only `cerf.exe` is insufficient.

## Verification

```powershell
python -m pip install PyYAML==6.0.1
python tools/validate_languages.py
python tests/i18n/test_catalog.py
python tests/i18n/test_launcher.py
```

The launcher test creates actual Tk windows and requires a desktop session.
It checks five consecutive language changes without changing the window/process,
search preservation, settings labels, properties labels, and icon resources.

Native tests build separately from the emulator:

```powershell
cmake -S tests/i18n -B build/i18n-tests -A Win32 `
  -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake `
  -DVCPKG_TARGET_TRIPLET=x86-windows-static
cmake --build build/i18n-tests --config Release
ctest --test-dir build/i18n-tests -C Release --output-on-failure
```

The native and Python tests cover Unicode text and paths, reordered/repeated
placeholders, escaped braces, missing/malformed catalogs, invalid schemas,
duplicate keys, language-code path traversal, and atomic failed reloads.
Catalog validation checks source references and placeholder parity. Partial
translations are permitted, and the validator reports English fallback counts
instead of hiding coverage gaps.

The conversion covers the main menus, input controls, battery, task manager,
shutdown and calibration dialogs, PCMCIA insertion submenus and CF image dialogs,
and common launcher dialogs, including configuration previews and board support.
Database display fields use keys derived from table, stable record ID and binding
IDs. Notes additionally use their position within their original record. The
English catalog must match the supplied field before an override is displayed;
new, reordered or edited metadata retains its supplied text. Database values,
file extensions, CPU option IDs and saved-state card IDs remain untranslated.

ROM producers may optionally add `meta.description_key` and `meta.note_keys` to
reference catalog messages. Original `description` and `notes` are retained for
older clients and unknown keys. `note_keys` aligns with `notes` by position; use
an empty string for an untagged note. This is another proposed metadata-schema
extension requiring maintainer discussion. Bundles without tags retain their
original text; this does not automatically translate arbitrary external content.

Externally supplied issue titles, diagnostic logs, and some device-specific
controls retain their original text. Catalog coverage counts
measure converted messages, not every string in the application. Korean, French,
Japanese, Russian and Polish cover the current default catalog in full. Brand
names, CPU instruction mnemonics, file formats and unit symbols retain their
standard spelling. Additional partial catalogs still use English fallback.

Parser references: [yaml-cpp tutorial](https://github.com/jbeder/yaml-cpp/wiki/Tutorial)
and [PyYAML documentation](https://pyyaml.org/wiki/PyYAMLDocumentation).
